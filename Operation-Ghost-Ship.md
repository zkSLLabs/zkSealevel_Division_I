## Operation Ghost Ship

Mission: Elevate zkSealevel from Devnet POC to a public, verifiable Solana Testnet deployment with production-grade cryptography, byte-precise protocol contracts, rigorous observability, and secure operations. All components MUST be real, reproducible, and auditable end-to-end.

This specification is normative. Terms such as MUST, MUST NOT, SHALL, SHOULD, and MAY follow RFC 2119 semantics.

---

### 1) Scope and Non-Goals

Scope:
- Implement, deploy, and operate a Testnet-ready system using real STARK proofs verified off-chain by the orchestrator and committed on-chain as byte-precise commitments.
- Maintain deterministic, byte-precise contracts across components (program, prover, orchestrator, indexer, DB).
- Provide a complete operational playbook: deployment, monitoring, incident response, and key management.

Non-Goals:
- On-chain proof verification (STARK) within BPF is out-of-scope; proofs are verified off-chain and committed on-chain via cryptographic commitments.
- Economic policies (slashing, rewards) are out-of-scope for this milestone.

---

### 1.1) Zero‑Mock/Placeholder Policy (Normative)

The following practices are explicitly FORBIDDEN in CI, staging, and Testnet:
- Mocked, stubbed, or simulated STARK proofs or verifiers. All proofs MUST be generated by the real Winterfell prover and verified by `stark-verify`.
- Bypassing or disabling `REQUIRE_STARK`. `/anchor` MUST fail if proof generation/verification is unavailable.
- Dummy keys or committed plaintext keys for aggregator signing. Testnet MUST use HSM-backed keys; file-based keys are permitted ONLY for local development.
- Fake program IDs, fake chain IDs, or bypassing DS/Ed25519 preflight. Transactions MUST include ComputeBudget  Ed25519  Anchor in the exact order.
- Mock RPC or DB layers (except for unit tests that do not exercise protocol paths). Integration/CI flows MUST use a real validator (local or Testnet) and a real PostgreSQL instance.

Requirements:
- CI integration and nightly runs MUST execute full STARK generation and verification and MUST anchor using the v2 instruction path (local validator acceptable for CI; Testnet for staging).
- Orchestrator MUST NOT call debug instructions (e.g., `ping`, `echo_accounts`) on Testnet.
- All persisted artifacts, proofs, and commitments MUST correspond to real cryptographic computations and MUST be auditable end-to-end.

### 6) Protocol Contracts (Normative, Byte-Precise)

#### 6.1 Domain Separation (unchanged from v1)
Length = 110 bytes (MUST be exact). Layout (offset, length, type):
- 0, 14, ASCII: `"zKSL/anchor/v1"` (bytes: 7A 4B 53 4C 2F 61 6E 63 68 6F 72 2F 76 31)
- 14, 8, u64 LE: `chain_id` (Testnet = 102; bytes: 66 00 00 00 00 00 00 00)
- 22, 32, bytes: `program_id` (raw 32-byte pubkey)
- 54, 32, bytes: `proof_hash` (Blake3 of canonical artifact JSON)
- 86, 8, u64 LE: `start_slot`
- 94, 8, u64 LE: `end_slot`
- 102, 8, u64 LE: `seq`

`ds_hash = blake3(DS_110_bytes)` (32 bytes).

Transaction instruction ordering (strict): ComputeBudget(SetComputeUnitLimit ≥ 200,000)  Ed25519(verify DS)  Anchor(`anchor_proof_v2`). Transactions MUST be rejected if the order deviates.

Example (Testnet binding, illustrative values; hex shown with spaces between fields, not stored):
```
"zKSL/anchor/v1" |
66 00 00 00 00 00 00 00 |
<32B program_id> |
<32B proof_hash> |
<8B start_slot LE> |
<8B end_slot LE> |
<8B seq LE>
 blake3  ds_hash (32B)
```

#### 6.2 Public Inputs (STARK)  V2
Canonical fields:
- `start_slot`: u64 (JSON number)
- `end_slot`: u64 (JSON number)
- `state_root_before`: 32-byte hex lowercase string
- `state_root_after`: 32-byte hex lowercase string
- `proof_hash`: 32-byte hex lowercase string
- `ds_hash`: 32-byte hex lowercase string

Canonical JSON MUST be produced using the project’s JCS-like canonicalizer (sorted keys, omit undefined, no extra whitespace). Two commitments:
- `stark_pi_hash = blake3(UTF8(canonical_json(PublicInputsV2)))` (32 bytes)
- `stark_proof_hash = blake3(proof_bytes)` (32 bytes), where `proof_bytes` are the exact Winterfell proof serialization.

Rationale: `stark_pi_hash` binds the proof’s public inputs to the DS/anchor context; `stark_proof_hash` binds to the concrete proof artifact to enable auditability and deduplication.

#### 6.3 Anchor Instruction (V2)  `anchor_proof_v2`
Discriminator: `sha256("global:anchor_proof_v2")[0..8]`.

Argument order (Borsh, MUST match function signature exactly). Offsets are relative to the start of the payload (immediately after the 8-byte discriminator):
- 0..15 (16): `artifact_id: [u8;16]`
- 16..47 (32): `proof_hash: [u8;32]`
- 48..55 (8): `seq: u64 LE`
- 56..63 (8): `start_slot: u64 LE`
- 64..71 (8): `end_slot: u64 LE`
- 72..75 (4): `artifact_len: u32 LE`
- 76..107 (32): `state_root_before: [u8;32]`
- 108..139 (32): `state_root_after: [u8;32]`
- 140..171 (32): `aggregator_pubkey: [u8;32]`
- 172..179 (8): `timestamp: i64 LE`
- 180..211 (32): `ds_hash: [u8;32]`
- 212..243 (32): `stark_pi_hash: [u8;32]`
- 244..275 (32): `stark_proof_hash: [u8;32]`

Payload length = 276 bytes. Total instruction data length = 8 (discriminator) + 276 = 284 bytes.

Account metas (order is normative):
1. `submitted_by` (signer, writable)
2. `config` (writable)
3. `aggregator_state` (writable, PDA)
4. `range_state` (writable, PDA)
5. `proof_record_v2` (writable, PDA; seeds: `["zksl","proof2", proof_hash, seq_le8]`)
6. `sysvar_instructions` (read-only)
7. `system_program` (read-only)

#### 6.4 Account Layout  `ProofRecordV2`
Data-only SIZE = 326 bytes. Fields and SIZE (in bytes), in order:
- `artifact_id` (16)
- `start_slot` (8)
- `end_slot` (8)
- `proof_hash` (32)
- `artifact_len` (4)
- `state_root_before` (32)
- `state_root_after` (32)
- `submitted_by` (Pubkey, 32)
- `aggregator_pubkey` (Pubkey, 32)
- `timestamp` (i64, 8)
- `seq` (u64, 8)
- `ds_hash` (32)
- `commitment_level` (u8, 1; 0 processed, 1 confirmed, 2 finalized)
- `stark_pi_hash` (32)
- `stark_proof_hash` (32)
- `da_params` (12; reserved)
- `reserved` (5)

Anchor alloc size (account data + discriminator) = 326 + 8 = 334 bytes.

Backward compatibility: v1 `ProofRecord` remains unchanged; v2 uses seed prefix `"proof2"`. The indexer MUST decode both.

### 7) STARK Design (Winterfell)  Real AIR for Testnet

#### 7.1 Goal
Prove a bounded, hash-linked transition from `state_root_before` to `state_root_after` across `[start_slot, end_slot]`, binding to `proof_hash` as domain separation. The AIR MUST be suitable for Testnet performance and auditable in code.

#### 7.2 AIR (Rescue-Prime based accumulator)
Let `steps = end_slot - start_slot + 1` (MUST satisfy `1 ≤ steps ≤ 2048`).
Define a Rescue-Prime permutation `H(x, slot, proof_hash)` with domain separation (e.g., prefix tag `"zksl::v2::acc"` and the `proof_hash` bytes absorbed prior to rounds).

Trace:
- Single main column `acc[i]` for `i = 0..steps`.

Constraints:
- Initial: `acc[0] == H(state_root_before, start_slot, proof_hash)`
- Transition: `acc[i+1] == H(acc[i], start_slot + i + 1, proof_hash)` for all `i in [0..steps-1]`
- Final: `acc[steps] == state_root_after`

PublicInputs for Winterfell proof object:
- `{ start_slot, end_slot, state_root_before, state_root_after, proof_hash }`

Commitments:
- `stark_proof_hash = blake3(proof_bytes)`
- `stark_pi_hash = blake3(UTF8(canonical_json({ start_slot, end_slot, state_root_before, state_root_after, proof_hash, ds_hash })))`

Security parameters:
- Field and extension per Winterfell defaults; rounds per Rescue-Prime such that ≥128-bit conjectured security at `steps ≤ 2048`. The exact round constants and rate/capacity MUST be pinned and committed.

#### 7.3 Prover CLI (Rust)
- `prover stark-prove --start <u64> --end <u64> --before <hex32> --after <hex32> --proof-hash <hex32> --out <path>`
- `prover stark-verify --proof <path>` (exit code 0 on success; non-zero on failure; MUST print JSON `{"status":"ok"}` on success).

Proof file format (JSON):
- `{ "public_inputs": { "start": <u64>, "end": <u64>, "before": "<hex32>", "after": "<hex32>", "proof_hash": "<hex32>" }, "proof_b64": "<base64>" }`

### 8) Program Changes (v2)

#### 8.1 New Instruction: `anchor_proof_v2`
Validation steps (MUST be enforced in this order where applicable):
1. `config.paused == 0`
2. Aggregator key rotation: compute allowed pubkey from `activation_seq` and compare to `aggregator_pubkey` arg.
3. Ed25519 preflight: Exactly one Ed25519 instruction present; MUST directly precede `anchor_proof_v2`.
4. ComputeBudget: Presence of `SetComputeUnitLimit(units ≥ 200,000)` anywhere in the transaction.
5. Domain separation: recompute DS from arguments; `ds_hash` MUST match arg; Ed25519 message MUST equal DS; Ed25519 public key MUST equal allowed aggregator key.
6. Monotonic seq: `seq` MUST equal `last_seq + 1` (or `1` for the first proof), then update `last_seq`.
7. Range contiguity and bounds: `end_slot ≥ start_slot`, `steps ≤ 2048`, `start_slot == last_end_slot + 1` (or `1` if first), then update `last_end_slot`.
8. Clock skew: `|Clock.unix_timestamp - timestamp| ≤ 120` seconds.
9. Idempotency: `proof_record_v2.seq` MUST be zero prior to write (no overwrite allowed).
10. Persistence: write `ProofRecordV2`, setting `stark_pi_hash` and `stark_proof_hash` exactly as provided.
11. Emit event with fields `{ artifact_id, proof_hash, seq, ds_hash, stark_pi_hash, stark_proof_hash }`.

#### 8.2 PDA
`ProofRecordV2` PDA seeds: `["zksl","proof2", proof_hash, seq_le8]` (MUST be little-endian for `seq`).

#### 8.3 Backward Compatibility
The v1 instruction and account remain valid. Orchestrator MUST use v2 on Testnet. Indexer MUST decode and persist both versions.

### 10) Orchestrator v2 (Server and API)

#### 10.1 Endpoints (unchanged paths; v2 behavior under the hood)
- `POST /artifact` — Validates and persists canonical artifact; returns `{ artifact_id, proof_hash }`.
- `POST /prove` — Optional convenience: generate STARK sidecar for slot window; returns `{ artifact_id, proof_hash, stark_proof_file }` when enabled.
- `POST /anchor` — Mandatory STARK verification; constructs DS; computes `stark_pi_hash` and `stark_proof_hash`; submits `anchor_proof_v2`; returns `{ aggregator_signature, ds_hash, transaction_id }`.
- `GET /proof/:artifact_id` — Returns artifact (if available) and latest on-chain status from DB.
- `GET /validator/:pubkey` — Returns validator registration status from DB.

All POST endpoints MUST require `Idempotency-Key` and MUST be rate-limited.

#### 10.2 Request/Response Schemas (normative excerpts)
`POST /anchor` request:
```
{ "artifact_id": "<uuid-v4>" }
```

`POST /anchor` response (200):
```
{ "aggregator_signature": "<hex-64>", "ds_hash": "<hex-64>", "transaction_id": "<base58>" }
```

Error responses MUST be of the form:
```
{ "error": { "code": "<PascalCase>", "message": "<string>", "details": <object|null> } }
```

#### 10.3 STARK Enforcement
On `/anchor`, the orchestrator MUST:
- Read artifact from disk if not cached.
- Recompute DS and `ds_hash` exactly per §6.1.
- Compose `PublicInputsV2` including `ds_hash`; canonicalize; compute `stark_pi_hash`.
- Verify STARK sidecar via `stark-verify` (exit code 0). On failure MUST return 400 `StarkVerifyFailed`.
- Compute `stark_proof_hash = blake3(proof_bytes)`.
- Encode `anchor_proof_v2` payload in exact order per §6.3 and submit transaction with strict instruction ordering.

### 11) Keys and Security

#### 11.1 Aggregator Key
- MUST be stored in an HSM or otherwise hardware-backed store in Testnet.
- Signing API MUST provide `ed25519_sign(message)` returning 64-byte signature; the public key bytes MUST be provided to configure on-chain `config`.
- Rotation:
  - Admin sets `next_aggregator_pubkey` and `activation_seq` via `update_config`.
  - Orchestrator MUST switch to new key at or after `activation_seq`.

#### 11.2 API Protections
- Rate limiting: token-bucket per source IP (default: 10 req/sec burst 20) and per-artifact idempotency.
- Schema validation: All JSON inputs MUST pass zod schema validation with explicit error messages.
- Logging: No secrets in logs. PII is not processed.

### 20) Risks and Mitigations

- RPC rate limits  exponential backoff with jitter; optional dedicated RPC endpoint.
- Ed25519 layout drift across SDK versions  unit tests parsing Ed25519 ix data; pin SDK versions.

- Key compromise  HSM enforcement; rotation procedure; least-privilege infra access.
